Discovery file — Engineering guide

What to Put in llms.txt for Your Brand

A production-grade /llms.txt is a small plain-text index at your canonical root: one verifiable H1, one blockquote definition, and a few Markdown sections linking to public pages you already maintain. This guide covers the proposed format, canonical-host and text/plain serving, pre-deploy validation, common trust failures, and a generation workflow from a reviewed brand facts library. The goal is a file you can regenerate and check after each deploy, not a new ranking lever.

1. The spec: what llms.txt is and is not

/llms.txt is a proposed convention documented at llmstxt.org and tracked in the Answer.AI llms-txt repository. It is deliberately small: a Markdown file at the site root that gives LLM crawlers and retrieval tools a concise, human-maintained summary of the site, with links to the full pages. Think robots.txt for intent: a hint, not a contract.

Key properties from the proposal:

  • Location: https://example.com/llms.txt at the root. Not /docs/llms.txt, not /static/llms.txt.
  • Format: Markdown rendered as plain text. No HTML, no YAML front matter, no JSON.
  • Audience: Crawlers that choose to look for it — GPTBot, CCBot, PerplexityBot and others that document Markdown discovery — plus developer tools that fetch it explicitly.
  • Status: Optional. No search engine or model provider guarantees consumption. A 200 response proves reachability, not readership.
  • Optional companion: /llms-full.txt may contain a concatenated dump of key pages, but the index file (llms.txt) is the entry point and should stay short.

The design goal is to solve a concrete failure: a crawler meets a JavaScript-heavy homepage, times out, and leaves with no anchor text for the brand. A 1–3 KB plain-text file with absolute links gives that same crawler a cheap, deterministic fallback. It is not a sitemap, not a knowledge graph, and not a place to pitch. If the content is not already stated on a public HTML page, it does not belong in the index.

Mental model: HTML is the source of truth. llms.txt is a curated table of contents with verified labels. If the two disagree, HTML wins and the index is wrong.

2. Markdown shape: the only structure you need

The proposal intentionally leaves Markdown permissive, but production discipline is stricter. The shape that validates cleanly with link checkers, parses without ambiguity, and stays LLM-friendly is:

# Brand Name

> One-sentence, verifiable description that already appears on the homepage.

## Official resources

- [Product](https://example.com/): Primary product page.
- [Docs](https://example.com/docs): Documentation home.
- [Pricing](https://example.com/pricing): Plans and billing.
- [Contact](https://example.com/contact): Contact and support.

## Verified facts

- Acme serves teams in the EU and US — see https://example.com/about.
- Pro plan includes SSO and audit logs — see https://example.com/pricing.

## Optional

- [Blog](https://example.com/blog): Product updates and guides.
- [Status](https://status.example.com/): Uptime and incidents.

Rules that prevent drift:

  • Exactly one H1 — the registered brand name. Not a tagline, not a keyword stuffing line. Match the <title> and Organization.name JSON-LD.
  • One blockquote directly under the H1 — a single verifiable sentence. Copy it verbatim from the homepage hero or meta description. If marketing rewrites the hero, this line must change in the same commit.
  • H2 sections only after that. The proposal mentions ## for sections; do not introduce ### unless a section genuinely needs subgrouping. Flat headings parse more reliably.
  • Lists are links with labels: - [Label](https://example.com/path): human-readable hint. Every link is absolute, https, and on the canonical host (or an explicit allow-list such as a status subdomain). No relative URLs, no anchors, no example.com/path without scheme.
  • Facts are claim plus source: - Claim — see https://example.com/source-page. The source URL must return 200 and contain the claim in HTML. This is how a reviewer checks the file without domain knowledge.
  • Line length: keep list items under 160 characters. Crawlers chunk by line; long paragraphs dilute the signal.
  • Encoding: UTF-8, LF line endings, no BOM. Trailing newline at EOF.

What not to add: code fences, tables, images, footnotes, HTML comments, or front matter. A parser that strips Markdown to plain text should still produce a readable file. If your file needs a table to explain pricing, your pricing page already failed — link to it instead.

3. Canonical host and location

/llms.txt is only useful at the canonical origin. A crawler that discovers https://example.com/ will probe https://example.com/llms.txt; it will not probe https://www.example.com/llms.txt if the canonical is apex, or vice versa.

  • Pick one canonical host and declare it in the H1 block and in <link rel="canonical">. If https://example.com is canonical, https://www.example.com/llms.txt must 301 to the apex path, not serve a second copy.
  • Serve only at /llms.txt (and optionally /llms-full.txt). Do not publish at /en/llms.txt or /blog/llms.txt. Language variants belong as linked pages inside the file, not as parallel indexes.
  • HTTPS only. Mixed-content checks and HSTS mean http should 301 to https. Crawlers that enforce https will ignore an http-only file.
  • No auth, no bot challenge. The path must return 200 to an anonymous GET. If your WAF challenges GPTBot on HTML, it will challenge it on llms.txt too — fix crawl access first (see GPTBot Blocked by robots.txt? Find and Fix the Rule).
  • Consistent trailing slash policy: /llms.txt is a file, never /llms.txt/. The latter should 404, not 301 to the file with a slash.

If you operate multiple domains (apex, app subdomain, docs subdomain), publish one file per registrable domain. docs.example.com/llms.txt should index docs, not duplicate the marketing site.

4. Serving as text/plain

The file is Markdown content served with a plain-text content type. That pairing matters: text/markdown is technically correct but text/plain; charset=utf-8 has broader crawler and CDN compatibility. The proposal and existing implementations converge on text/plain.

Required headers:

Content-Type: text/plain; charset=utf-8
Content-Length: <bytes>
Cache-Control: public, max-age=3600, stale-while-revalidate=86400
X-Content-Type-Options: nosniff

Implementation notes by stack:

  • Nginx (static file): 
    location = /llms.txt {
  default_type text/plain;
  charset utf-8;
  add_header Cache-Control "public, max-age=3600, stale-while-revalidate=86400" always;
  add_header X-Content-Type-Options nosniff always;
  # file lives at /var/www/site/llms.txt
}
  • Cloudflare / CDN: cache the path at the edge but purge on deploy. Set a single Cache Rule for /llms.txt and /llms-full.txt — do not inherit a blanket cache-everything that pins stale pricing for days.
  • Vercel / Next.js: place llms.txt in public/. Next will serve it as text/plain automatically, but add a headers() entry in next.config.js to set charset and Cache-Control explicitly: 
    // next.config.js
async headers() {
  return [{
    source: '/llms.txt',
    headers: [
      { key: 'Content-Type', value: 'text/plain; charset=utf-8' },
      { key: 'Cache-Control', value: 'public, max-age=3600, stale-while-revalidate=86400' },
    ],
  }];
}
  • S3 + CloudFront: set ContentType: text/plain; charset=utf-8 on upload. S3 defaults to binary/octet-stream if you omit it.

Do not serve the file through client-side JS, edge workers that inject HTML wrappers, or localized middleware that appends a banner. curl -s https://example.com/llms.txt | head -c 200 should return Markdown bytes, not <!doctype.

5. What belongs in the file

Every line must satisfy two gates: it is already published in public HTML, and a stranger can verify it by opening one link. The minimal useful set is:

  • Brand name and one-sentence definition — the same string that appears in the homepage H1 or meta description. No superlatives.
  • Canonical site URL — one line, not a paragraph. Example: Site: https://example.com/ or the H1 itself if the brand name resolves.
  • Official resources (4–8 links): product, pricing, docs, contact, plus at most two editorial hubs (blog, changelog, status). Each label is stable across deploys.
  • Verified facts (3–6 bullets): markets served, compliance posture, plan names, or integration claims — each paired with the page that states it. If the fact lives only in a slide deck, it does not go in.

Keep the file under 5 KB. A crawler that already struggles with your homepage will not benefit from a 2,000-word manifesto. Short, link-dense files get fetched, cached, and chunked more reliably than long essays.

Alignment check: Organization.name and Organization.description in your JSON-LD, the homepage hero, and the llms.txt H1 + blockquote should be identical or trivially reconcilable. A reviewer diffing the three should see no drift.

6. What to leave out — anti-patterns

Most llms.txt failures are not syntax errors; they are trust errors. These patterns reliably cause a reviewer or retrieval system to discount the file.

Stale pricing (the top failure)

Copying a pricing table into llms.txt and then updating the pricing page but not the file is the fastest way to teach a crawler that your index is unreliable. If you must mention pricing, do it as a pointer, not a copy:

- Pricing: https://example.com/pricing — plans, billing interval, and current prices live on this page.

Do not write - Pro: $49/mo unless the same source renders the pricing page and the index in one deploy. In CiteAura, a generated asset with an unsynchronized or unreviewed fact is held for review; the platform does not publish it to your site.

Other anti-patterns

  • Unverifiable claims: Awards, traffic numbers, or “#1 in AI search” without a public page that states the methodology. Leave them out.
  • Competitor attacks: Factual comparison copy you would publish on a /compare page is fine; ad-hominem or un-sourced claims are not.
  • Private and staging routes: /admin, staging.example.com, login-walled docs, Notion links, or PDFs behind auth. If the URL requires a cookie, the crawler cannot verify it.
  • Slogan soup: Lists of adjectives with no links. Every line without a URL is a line a model must take on faith.
  • Duplicated sitemaps: Dumping 200 URLs into llms.txt adds no value over sitemap.xml. The file is a curated index, not an enumeration.
  • Locale forking: Do not create /fr/llms.txt alongside the root file with conflicting facts. Link to https://example.com/fr/ inside the single root file instead.
  • SEO bait and switch: Keywords in llms.txt that do not appear in HTML. Consistency checks will flag the mismatch.

Rule of thumb: If you would not keep the line correct for 90 days without thinking about it, it does not belong. Facts rot; links to living pages do not.

7. Schema-style validation before deploy

A short file is easy to review by eye once. It is easy to break silently on every deploy after that. Validate the file in CI the same way you validate an API schema: parse, check structure, assert invariants, fail the build.

Invariants to enforce:

  • Exactly one H1, starts with # , length 2–60 chars, matches your brand registry.
  • One blockquote line directly after H1, 20–200 chars, no links inside the quote.
  • H2 sections from an allow-list: Official resources, Verified facts, Optional. No other H2 unless explicitly added to the allow-list.
  • Every list item contains an absolute https:// URL on the canonical host or allow-listed subdomain. No relative links, no http, no bare domains.
  • Every Verified facts bullet contains a — see https:// suffix or an inline link. No orphan claims.
  • No forbidden sections: Pricing as a standalone H2 with naked prices is rejected — use a link instead.
  • File is UTF-8, LF, ends with newline, under 5 KB.

Example validation with Zod (TypeScript). Adapt the schema to your stack, but keep the same predicates:

import { z } from "zod";

const CanonicalUrl = z.string().url().refine(
  (u) => u.startsWith("https://example.com/") || u.startsWith("https://status.example.com/"),
  "URL must be on the canonical host or allow-list"
);

const LlmsTxt = z.object({
  h1: z.string().min(2).max(60),
  tagline: z.string().min(20).max(200),
  sections: z.array(z.object({
    heading: z.enum(["Official resources", "Verified facts", "Optional"]),
    items: z.array(z.object({
      label: z.string().min(2).max(80),
      url: CanonicalUrl,
      hint: z.string().max(120).optional(),
      source: z.string().url().optional(), // required for Verified facts
    })).min(1).max(12),
  })),
  raw: z.string().max(5120).refine(s => s.endsWith("\n"), "must end with newline")
    .refine(s => !s.includes("\r"), "LF only")
    .refine(s => (s.match(/^# /gm) || []).length === 1, "exactly one H1"),
});

// Usage in CI: parse Markdown to LlmsTxt shape, then LlmsTxt.parse(obj).
// Extra checks: fetch every URL, assert 200, assert claim substring in HTML.

const FORBIDDEN = [/^\$\d+/, /#1 in/i, /staging\./i];
function noForbidden(s: string) {
  for (const re of FORBIDDEN) if (re.test(s)) throw new Error(`Forbidden pattern ${re} in: ${s}`);
}

For Python pipelines (closer to the CiteAura engine style), the same checks translate to pydantic or plain regex guards in scripts/validate_llms.py. The important move is not the library — it is failing the deploy when the file drifts.

Live link checks should run after the preview deploy, not just on the Markdown string. Fetch each URL, assert 200, assert the response is text/html with the claim substring, and assert robots.txt does not block the path for the crawler you care about.

8. Generation pipeline: from fact library to file

Hand-editing llms.txt scales to one site and one owner. Teams need a pipeline that treats the file as a built artifact, not a hand-maintained page.

Source of truth: the brand fact library. In CiteAura this is the same registry that feeds JSON-LD, homepage copy, and the brand fact pack: brand name, canonical URL, one-sentence definition, resource links, and a small set of verified facts each paired with a source URL. Facts that lack a source URL cannot be selected for llms.txt — the UI disables the toggle.

Pipeline steps (single deploy, atomic):

  1. Collect: read the fact library (stored alongside work/<tenant>/<slug>/brand.json or your CMS). Resolve canonical host, resource list, and enabled facts.
  2. Filter: drop any fact whose source URL is not 200 at build time, any resource whose target is not public, and any label that fails the Zod schema. Emit warnings, not silent drops.
  3. Render: template to Markdown. Keep the renderer trivial — string interpolation, no Markdown library — so the output is deterministic. 
    # ${brand.name}

> ${brand.tagline}

## Official resources
${resources.map(r => `- [${r.label}](${r.url}): ${r.hint}`).join("\n")}

## Verified facts
${facts.map(f => `- ${f.claim} — see ${f.source}`).join("\n")}

## Optional
${optional.map(r => `- [${r.label}](${r.url}): ${r.hint}`).join("\n")}
  4. Validate: run the Zod/pydantic schema and live link checks against the preview URL. Fail if any invariant breaks.
  5. Write: emit public/llms.txt (or dist/llms.txt) as UTF-8 LF. Do not pretty-print, do not inject build metadata comments.
  6. Deploy atomically: the file ships in the same artifact as the HTML it indexes. No separate manual upload that can lag behind a pricing change.

Keep the pipeline stateless. The file at https://example.com/llms.txt should be reproducible from the commit that produced the HTML. If you cannot regenerate the file from main without a manual step, the next on-call rotation will ship a stale file.

Scheduling: rebuild on every content deploy, not on a cron. A nightly cron that regenerates the file without re-validating HTML consistency recreates the stale-pricing problem on a timer.

9. Deployment

Ship the file the same way you ship HTML: as part of the build artifact, cached at the edge, purged on deploy.

  • Static hosts (S3, GCS, Netlify): include llms.txt in the upload set. Set Content-Type explicitly on upload; object storage will not infer charset=utf-8.
  • CDN (Cloudflare, Fastly, CloudFront): add an explicit cache rule for the path. After deploy, purge /llms.txt by URL. Do not rely on TTL alone if you change pricing mid-day.
  • Container / Nginx: bake the file into the image at /usr/share/nginx/html/llms.txt or mount it from the same volume as the rendered site. A sidecar that writes the file after the container starts introduces a race.
  • Preview deploys: do not expose llms.txt on preview hosts with the production canonical URL inside. Either omit the file on previews or render it with the preview host as canonical and block indexing via X-Robots-Tag: noindex.

Do not gate the path behind authentication, A/B middleware, or geo-blocking. A crawler from us-east-1 must see the same bytes as a browser in Berlin. If you run edge personalization, exclude /llms.txt and /llms-full.txt from the variant logic.

10. Verification: curl and CI

Verification has two layers: the file is correctly served, and its claims still match the live site. Both belong in CI and in a post-deploy smoke check.

Manual curl checks (run after every deploy)

# 1. Status, content-type, and cache headers
curl -i https://example.com/llms.txt

# Expected:
# HTTP/2 200
# content-type: text/plain; charset=utf-8
# cache-control: public, max-age=3600, stale-while-revalidate=86400
# x-content-type-options: nosniff

# 2. Body sanity — no HTML wrapper
curl -s https://example.com/llms.txt | head -n 20
# Should start with "# Brand Name" and "> "

# 3. No redirect on the canonical host (www should redirect, canonical should not)
curl -i https://www.example.com/llms.txt
# Expected: 301 to https://example.com/llms.txt if apex is canonical

# 4. Every link in the file returns 200 and is not blocked by robots
grep -oE 'https://[^) ]+' https://example.com/llms.txt | while read url; do
  echo "→ $url"
  curl -s -o /dev/null -w "%{http_code} %{content_type}\n" "$url"
done

# 5. Robots allows the file and its targets for the crawler you care about
curl -s https://example.com/robots.txt | grep -i -A2 -B2 "llms"
curl -s https://example.com/robots.txt | grep -i "gptbot"

# 6. Charset and line endings
curl -s https://example.com/llms.txt | file -
# Expected: ASCII text, with very long lines, UTF-8 Unicode text
curl -s https://example.com/llms.txt | cat -A | head -n 5
# Lines should end with $ (LF), not ^M$ (CRLF)

CI smoke (fail the pipeline if any check fails)

#!/usr/bin/env bash
set -euo pipefail
HOST="https://example.com"
FILE="$HOST/llms.txt"

# headers
ctype=$(curl -s -D - "$FILE" -o /tmp/llms.txt | tr -d '\r' | grep -i '^content-type:' | cut -d' ' -f2-)
[[ "$ctype" == "text/plain; charset=utf-8"* ]] || { echo "bad content-type: $ctype"; exit 1; }

# shape
grep -q '^# ' /tmp/llms.txt || { echo "missing H1"; exit 1; }
[[ $(grep -c '^# ' /tmp/llms.txt) -eq 1 ]] || { echo "more than one H1"; exit 1; }
grep -q '^> ' /tmp/llms.txt || { echo "missing blockquote tagline"; exit 1; }
grep -q '^## Official resources' /tmp/llms.txt || { echo "missing Official resources"; exit 1; }

# size
bytes=$(wc -c < /tmp/llms.txt)
(( bytes < 5120 )) || { echo "file too large: $bytes bytes"; exit 1; }

# links
grep -oE 'https://[^) ]+' /tmp/llms.txt | while read url; do
  code=$(curl -s -o /dev/null -w "%{http_code}" "$url")
  [[ "$code" == "200" ]] || { echo "broken link $url: $code"; exit 1; }
done

echo "llms.txt OK ($bytes bytes)"

Run the CI check against the preview deploy URL before promoting to production, and again against production after promotion. A file that passes in preview but fails in production means the CDN is serving a stale cached copy — purge and re-check.

The generator checks one H1, approved sections, absolute HTTPS URLs, and a source for each fact. 12. Publishing llms.txt does not guarantee mentions

A clean file can help a retrieval-enabled sample find official wording without scraping a heavy homepage. It does not guarantee that ChatGPT, Claude, Perplexity, or any other model will mention, cite, or rank the brand. Models vary in whether they fetch the file, how they chunk it, and how they weigh it against other sources.

Treat llms.txt as one official summary next to the HTML that already has to be extractable. If the homepage is blocked by robots, if the pricing page disagrees with the index, or if the only source for a claim is the index itself, the index will be ignored — correctly. The file earns trust by staying small, correct, and boring. Keep it that way and it compounds; let it drift and it teaches every crawler to skip you.

If GPTBot cannot reach the homepage at all, fix crawl access first. See GPTBot Blocked by robots.txt? Find and Fix the Rule.

FAQ: publishing llms.txt

What should not go in llms.txt?

Leave out private routes, staging URLs, login-only content, credentials, and claims that are not supported by an official public page. Never duplicate pricing as bare numbers — link to /pricing instead. If the source page changes, the file would otherwise go stale and break trust.

Does llms.txt guarantee AI mentions?

No. It is an optional discovery convention. A reachable file does not prove that a model read it or will mention the brand. Verify what you can: the file is text/plain; charset=utf-8, every link is 200, and every claim appears in HTML.

Where should llms.txt be published?

Publish it as plain text at the canonical site root, for example https://example.com/llms.txt, and keep its links public. Serve it from the single canonical host (apex or www), allow anonymous GET, and return Cache-Control that matches how often facts change. Purge the CDN on deploy.

How do I validate llms.txt before deploy?

Parse the Markdown in CI, enforce one H1 plus allow-listed H2s, assert every URL is absolute https on your canonical host, require a source URL per fact, and reject naked pricing or forbidden patterns. Then fetch every URL from the preview deploy and assert 200 plus claim presence. Fail the build on any violation.
