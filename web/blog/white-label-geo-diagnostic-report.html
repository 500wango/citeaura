Agency delivery — Technical specification

White-Label GEO Diagnostic Reports for Agencies

A white-label GEO diagnostic report is a versioned, client-ready artifact that proves what the site does and does not expose to AI retrieval, what sampled models actually said, and which tickets the client must ship to change the odds. It carries agency branding on the cover, not the vendor's. It is a point-in-time evidence pack — audit, tickets, verification — compiled from the current workspace state and hashed at build time. This spec documents the delivery pack structure, header injection, ticket lifecycle, verification evidence model, and the handoff checklist CiteAura uses for agency delivery.

Updated 24 August 2026 · 12 min read · Technical specification

By CiteAura Editorial Team

By James Liu — Agency Solutions Architect · CiteAura Delivery Engineering

1 — What the report is and is not

A diagnostic report is not a dashboard, not a forecast, and not a guarantee that ChatGPT, Perplexity, or Gemini will mention the client. It is a dated artifact with three properties an agency can hand to a client and defend in a meeting:

  • Site findings are falsifiable. Every claim maps to a crawl observation — HTTP status, rendered HTML hash, robots.txt rule, heading tree, structured data parse, or extractability probe — with a timestamp and a URL.
  • Samples are labeled. Each answer row carries question, raw answer, date, market/language, sampling mode (API · Model knowledge, API · Web-grounded retrieval, or Manual · Product surface), model identifier, and the exact string rule used to mark a mention. An unlabeled screenshot is not a cohort.
  • Actions are ticketed. Every finding that requires a change becomes a ticket with owner, target page, requested diff, acceptance check, and state. A slide that says "improve AI visibility" without a file path is not an action.

Readiness is split into three independent states: diagnosis (audit complete), visibility (sample cohort complete), and implementation (assets generated and reviewed). A pack can be client-ready for diagnosis while generated pages still require editorial review. Do not ship assets marked needs_review.

Invariant: A diagnostic ZIP is a snapshot. If the site, question set, audit parameters, or verification evidence change after the build timestamp, rebuild. The previous ZIP is historical evidence, not the current workspace.

2 — Delivery pack structure: documents, evidence, and assets

CiteAura compiles the pack as a deterministic ZIP from work/<tenant>/<slug>/delivery/. The build reads the current audit.json, tasks.json, metrics/, and delivery/ state, then adds the numbered reports, implementation assets, filtered raw-answer evidence, and a comparable before/after visibility file when the runs match. Every file is part of a timestamped snapshot with workspace metadata and SHA-256 hashes.

# Document Filename Contents
01 Executive Summary 01-Audit-Report.html One-page verdict: visibility posture (Blocked / Partial / Exposed), cohort mention rate with n and mode, top 3 blockers, and ticket count by severity. Written for the client decision-maker; no tool chrome.
02 Site Audit Report 02-Execution-Plan.html Per-URL findings: crawlability, HTTP status, HTML extractability, heading hierarchy, structured data (JSON-LD / Open Graph), robots.txt mapping, and WAF/auth wall detection. Each row links to raw evidence.
03 AI Visibility Matrix 03-Ticket-Log.html Cohort table: question × sampling mode × mention (yes/no) × citation (yes/no). Cohort definition, question set hash, model IDs, dates, and market. Unmeasured providers shown as unmeasured, never 0%.
04 Action Matrix & Tickets 04-Acceptance-Checklist.html Ticket log with ID, severity (P0/P1/P2), target file/URL, requested change (diff), owner, dependency, and acceptance check. Exported from tasks.json with lifecycle state.
05 Verification Evidence 05-Draft-Risks.html Before/after evidence per ticket: crawl snapshots, HTTP headers, HTML diff hash, structured data validator output, and re-sample cohort if applicable. Each ticket references its evidence page.
06 Implementation Guide 06-Build-Map.html Sequenced rollout plan: prerequisites, deploy order, rollback notes, and re-verification triggers. Links into the assets/ folder for the exact files to ship.
— Implementation Assets assets/ Generated files ready for review: llms.txt, robots.txt.patch, JSON-LD blocks, page patches, and validation reports. Every asset carries a status: draft | reviewed | approved flag. Draft assets are listed but flagged not for deploy.

The current evidence additions are explicit: 07-Evidence/raw-ai-answers.jsonl, 07-Evidence/raw-ai-answers.html, and 07-Evidence/citation-evidence.csv preserve the filtered answers and citations used in the cycle. 08-Before-After/visibility-delta.md and its HTML rendering compare two runs only when provider, model, question, and sampling mode are comparable; otherwise the report says comparison unavailable.

Ancillary files in the ZIP root:

  • manifest.json — build metadata: build_id, built_at, workspace_slug, question_set_hash, audit_hash, file list with SHA-256 per document.
  • README.txt — one-paragraph reading order for the client and a note that the pack is a point-in-time snapshot.
  • raw/ (optional) — machine-readable exports: audit.json, tasks.json, samples.csv for the client's own analysis. Included only when the agency enables "Include raw exports" at build time.

3 — White-label header injection

White-label is not a logo swap. It is a build-time header injection that replaces every occurrence of vendor identity with agency identity before the PDF renderer runs. The agency config lives at Delivery → White-Label Branding and is tenant-scoped.

Configuration surface

  • Agency name — legal or trading name rendered on the cover and every page header.
  • Logo — SVG or PNG, max 512 KB, rendered at 140×32 px in the header bar. Transparent background recommended; the build pipeline rejects logos with embedded scripts.
  • Domain and contact — agency domain (e.g. acme-digital.com) and optional contact email for the cover block.
  • Confidentiality notice — free-text footer, e.g. "Confidential — Prepared for [Client Name] by [Agency]. Do not distribute."
  • Accent color — hex token injected into the PDF stylesheet for headers, table rules, and callout borders. Defaults to the agency's brand token if unset.
  • Cover toggle: vendor attribution — when off (default for white-label), no CiteAura mark appears in the client-facing documents. The workspace UI still shows the vendor for the agency operator; the ZIP does not.

Build-time injection pipeline

  1. Operator clicks Build Pack. The API snapshots the current branding config and writes it to delivery/branding.json alongside the build.
  2. The renderer loads the branding snapshot, injects it into the header template (delivery/templates/header.html), and stamps it during document rendering. Headers are part of the layout pass, not post-processed watermarks.
  3. The manifest records branding_hash so a later rebuild with a changed logo or name is auditable as a distinct build.
  4. Raw exports in raw/ are not branded — they are machine-readable data. If the engagement requires white-label raw exports, the agency re-exports through its own template.

Check before you send. Open 01-Audit-Report.html and confirm the header shows the agency, not the vendor. Branding is snapshotted at build time.

Header injection is idempotent: rebuilding with identical branding and identical workspace state produces byte-identical PDFs except for the built_at timestamp in the footer. That timestamp is intentional — it is the snapshot claim.

4 — Ticket lifecycle

Findings become tickets so they can be assigned, shipped, and verified. CiteAura tracks them in tasks.json and exports the ticket log and acceptance checklist.

State Meaning Exit condition
OPEN Finding confirmed by audit; ticket created, not yet assigned. Owner assigned, target file/URL specified.
IN_PROGRESS Owner is implementing the diff. Change deployed to the canonical host (not staging).
IN_REVIEW Change is live; awaiting verification evidence. Re-crawl or re-sample evidence collected.
VERIFIED Acceptance check passed against live evidence. Agency marks ticket verified; evidence page linked.
CLOSED Verified and included in the delivery pack snapshot. Pack rebuilt; manifest hashes the closed state.
BLOCKED External dependency (e.g. client CMS access, CDN cache) prevents verification. Dependency resolved; ticket returns to IN_REVIEW.

Every ticket carries a fixed schema:

  • id — e.g. GEO-017, stable across rebuilds.
  • severity — P0 (blocks retrieval), P1 (degrades extraction), P2 (polish / structured data).
  • target — URL or file path (e.g. https://client.com/robots.txt, /products/widget.html).
  • finding — one-sentence audit observation with evidence pointer.
  • requested_change — unified diff or explicit instruction, not "optimize."
  • owner — agency or client assignee.
  • acceptance_check — the exact probe that will mark the ticket verified (e.g. "fetch /robots.txt on canonical host; confirm Allow: /products/ for GPTBot; re-crawl returns extractable: true").
  • evidence_ref — reference into the generated 07-Evidence/ files once verified.

Tickets are the only place where action lives. If a finding is not ticketed, it is not tracked, not verified, and not included in the implementation guide's deploy order. The action matrix is sorted P0 → P2, then by dependency, so the client knows what to ship first.

5 — Verification evidence

Verification is the gate between "we shipped a change" and "the change is proven on the live site." Without it, a pack is a plan, not a delivery. CiteAura treats verification as a re-crawl contract with three evidence types:

  • Site re-crawl evidence — a fresh fetch of the target URL after deploy: HTTP status, response headers, HTML hash, rendered extractability probe, structured data validation, and robots.txt rule evaluation. Stored as a dated snapshot next to the original audit snapshot so before/after is diffable.
  • Header and file evidence — for robots.txt, llms.txt, and similar root files: the raw file body, the matched User-agent group, and the Allow/Disallow evaluation per public path. A CDN or edge cache hit is flagged as stale until purged and re-fetched.
  • Re-sample evidence — an optional new cohort using the same question set and sampling mode after the ticket ships. This is a new measurement, not a warranty. The re-sample cohort is labeled with its own date and cohort_id and shown alongside the baseline, never merged into it.

Evidence is collected by the Verify & Deliver job (/docs#verification-delivery). The job re-runs the probes that correspond to the ticket's acceptance check, writes the evidence snapshot to delivery/evidence/<ticket_id>/, and updates tasks.json from IN_REVIEW to VERIFIED only when the acceptance predicate passes. A failed check leaves the ticket in IN_REVIEW with the failure reason recorded.

Do not conflate verification with mention improvement. Verifying that GPTBot can now fetch /products/ is a site fact. Measuring whether mentions rose from 2/20 to 7/20 on the same cohort after the fix is a separate sample fact. The pack reports both, on different pages, with different timestamps.

Each page in 05-verification-evidence.pdf carries: ticket ID, target, acceptance check, before hash, after hash, timestamp of the re-crawl, and the operator who triggered verification. If the evidence hash matches the audit hash, the page is marked no change detected — not verified.

6 — Agency workflow (from intake to handoff)

The workflow is designed so a junior operator can run it and a senior can audit it. All state lives on the filesystem under work/<tenant>/<slug>/; the database only tracks project index and job metadata.

  1. Intake — create project and run audit. Create the project with the client's canonical domain, market, and language. Run the site audit and review the audit report for P0 blocks before sampling.
  2. Sample — run a labeled cohort. Configure the question bank, select a sampling mode, and run the cohort. The ticket log and evidence exports retain the cohort ID, question set hash, and mode; unmeasured providers remain unmeasured.
  3. Ticket — convert findings to tickets. The audit auto-generates tickets for each finding (robots block, extractability failure, missing JSON-LD, heading structure). Operators triage severity, assign owners, and edit the requested diff. Every ticket must have an acceptance check before it leaves OPEN.
  4. Brand — configure white-label. Under Delivery → White-Label Branding, set agency name, logo, domain, confidentiality notice, and accent color. Save, then trigger a pack build and verify the header on the generated report.
  5. Build — compile the pack. Click Build Pack. The job writes the numbered documents, evidence directories, assets/, and manifest.json. Review readiness: diagnosis and visibility can be green while implementation assets are still draft.
  6. Verify — re-crawl after deploy. After the client ships a ticket, run Verify on that ticket. The pipeline re-crawls the target, evaluates the acceptance check, and promotes the ticket to VERIFIED only on pass. Rebuild the pack so the new evidence page and closed ticket state are included.
  7. Handoff — deliver the ZIP and the checklist. Send the ZIP with the client handoff checklist (Section 8). Include the reading order: executive summary → audit → visibility matrix → action matrix → evidence → implementation guide. Raw exports are optional and off by default.

The entire cycle is repeatable: audit → sample → ticket → brand → build → verify → rebuild. Each rebuild gets a new build_id and built_at. Old packs are retained as historical snapshots; only the latest build is "current."

7 — Pricing tiers

Agencies typically productize the diagnostic as a tiered engagement: a one-time audit, a recurring monitoring retainer, or a delivery retainer that includes verification. The tiers below reflect common CiteAura agency packaging; actual pricing is set by the agency and enforced via the tenant plan in the workspace.

Tier Includes Pack contents Verification
Diagnostic
One-time		 Site audit + 1 labeled cohort (single sampling mode) + ticket log. Docs 01–04 + manifest. Assets folder with draft llms.txt / JSON-LD marked not-for-deploy. No re-crawl. Tickets remain OPEN; handoff is diagnosis-only.
Diagnostic + Verify
Project-based		 Everything in Diagnostic plus acceptance checks and one re-crawl pass after client deploy. Numbered documents + 07-Evidence/, 08-Before-After/, and reviewed assets/. One verification cycle. Tickets promoted to VERIFIED on pass; pack rebuilt.
Retainer
Monthly		 Recurring audit + cohort re-samples (same question set) + ongoing tickets + raw exports. Full pack on each cycle + raw/ exports + cohort-over-cohort delta page in Doc 03. Continuous: verification on every ticket close; cohort comparison is a new measurement, not a promise.

Workspace plans are trial, starter, pro, agency, and enterprise; quotas such as sample runs and active projects are enforced per tenant. BYOK is supported: the encrypted tenant key is injected at runtime and is not included in the delivery pack.

8 — Client handoff checklist

Before you send the ZIP, run this checklist. It exists to prevent the two most common agency errors: shipping draft assets and shipping an outdated snapshot.

  • Branding verified — opened the generated audit report; header shows agency name/logo/domain, no vendor mark.
  • Build is current — manifest.json:built_at is after the last site change, question set edit, or verification run.
  • No draft assets in the deploy path — assets/ files marked draft are flagged not-for-deploy; only reviewed or approved assets are listed as shippable in the build map.
  • Acceptance checks are explicit — every ticket in the acceptance checklist has a written acceptance check; no ticket says "optimize" or "improve visibility."
  • Verification evidence attached — every verified ticket has evidence in 07-Evidence/ with the applicable crawl or sample details. Unverified tickets remain in review.
  • Cohort is labeled — the ticket log and evidence exports retain question set hash, sampling mode, model ID, date, and market. No screenshot is presented as a baseline.
  • No guarantees — the pack and the cover email contain no language promising mentions, citations, or rankings. The executive summary states the pack is a point-in-time evidence trail.
  • Raw exports gated — raw/ is included only if the engagement explicitly includes machine-readable exports; otherwise it is omitted.
  • Reading order communicated — cover email points the client through the numbered reports, then Evidence and Before-After, without jumping to draft assets.

If any box is unchecked, do not send. Fix the workspace state, rebuild, and re-check. A rebuilt pack is cheap; a client deploying a draft llms.txt with unchecked claims is not.

9 — Anonymized case: B2B SaaS site, 19 tickets, 2 verification cycles

Client profile: Series B B2B SaaS, ~180 marketing pages, docs on a subdomain, pricing behind a JS pricing widget. Domain anonymized as client-example.com. Market: en-US. Agency: mid-size performance agency reselling GEO diagnostics as a project engagement (Diagnostic + Verify tier).

Illustrative baseline (Build 1 — 2026-07-09): An anonymized B2B SaaS audit flagged extractability and robots issues, and a 20-question API · Model knowledge sample returned 2 mentions (10%). The agency packaged the findings with white-label headers and marked implementation assets as draft. These values describe an example workflow, not a CiteAura customer result.

Client deploy and verification cycle 1 (Build 2 — 2026-07-22): Client shipped 9 tickets: server-rendered the product pages, removed the stale /docs/ disallow, fixed heading structure on 4 pages, and added SoftwareApplication + FAQPage JSON-LD. Verification re-crawl: extractability flipped to true on 94% of product URLs, structured data validator passed on 6/6 target pages, and robots.txt evaluation showed GPTBot Allow: /docs/. Six tickets promoted to VERIFIED; three remained IN_REVIEW due to a CDN cache serving stale HTML (evidence page marked stale edge — purge and re-verify).

Verification cycle 2 and re-sample (Build 3 — 2026-07-30): After cache purge, the remaining 3 tickets verified. The agency ran a re-sample with the same 20 questions and same sampling mode (new cohort_id, 7 days after deploy). The re-sample cohort returned 8 mentions (40%) — a delta of +30 pp on the same question set. The pack's Doc 03 showed the two cohorts side by side with their cohort_id, dates, question set hash (identical), and sampling mode (identical), labeled as two separate measurements. The implementation assets for llms.txt were reviewed and moved from draft to reviewed in this build.

What the pack did not claim: No page promised that ChatGPT would now always mention the client, or that the 40% rate would hold for different questions, markets, or product surfaces. The executive summary stated: "Evidence trail for cohort co-07-30 on 20 buyer questions, en-US, API · Model knowledge. A different question set, sampling mode, or product surface is a new cohort." That language is load-bearing — it is what keeps the pack defensible when the client tests a new question next month.

10 — What must stay out of a client pack

  • Unlabeled screenshots from a single ChatGPT session presented as a baseline or a trend.
  • Assets still marked draft or needs_review, including unchecked llms.txt or JSON-LD with unvalidated claims.
  • Guaranteed mention, rank, or citation language. That claim is false and will not survive a re-sample.
  • Internal tool chrome, vendor branding (when white-label is engaged), or workspace screenshots that expose the measurement vendor.
  • Merged cohorts — two samples with different question sets, models, or surfaces averaged into one percentage.
  • Unmeasured providers shown as 0%. Unmeasured is unmeasured; it is not a data point.

11 — How to present it without overclaiming

Lead with what to change on the site. Put the mention rate next to the sample count, sampling mode, question set hash, and date — never alone. If a provider was not measured, say unmeasured. If the sample is API · Model knowledge, say so; do not imply it was the ChatGPT product UI.

A later sample after tickets ship is a new cohort, not a warranty. Show it as a second row in the visibility matrix with its own cohort_id, not as a projection. The pack gives the agency a repeatable evidence trail; it does not guarantee that any model will mention, cite, or rank the client for any future question.

Setup is in Verify & Deliver. Measurement method is in How to Measure ChatGPT Brand Mentions. For crawl blocks that require a fix before any sample is meaningful, see GPTBot Blocked by robots.txt.

FAQ: white-label GEO reports

What belongs in a white-label GEO diagnostic report?

Site findings with evidence pointers, labeled samples, action tickets with acceptance checks, raw answer and citation exports, before/after visibility when comparable, and clear readiness states. The exact files are listed in the delivery manifest.

Can a GEO diagnostic report guarantee AI mentions?

No. It records a dated evidence trail and the actions to take; it does not guarantee a future mention, citation, or ranking. A re-sample after a fix is a new cohort with its own cohort ID, not a warranty.

When should an agency rebuild a GEO diagnostic pack?

Rebuild after the site, question set, audit parameters, branding config, or verification evidence changes. The manifest's built_at and content hashes make the snapshot current; an older ZIP is historical.

How does white-label header injection work?

Agency branding (name, logo, domain, confidentiality notice, accent color) is configured under Delivery → White-Label Branding and injected at build time into the client-facing documents. No vendor cover remains in the white-label ZIP.

What triggers a ticket state transition?

Re-crawl or re-sample evidence that satisfies the ticket's written acceptance check. The Verify job promotes IN_REVIEW to VERIFIED only on pass; a failed check leaves the failure reason recorded and the ticket in review.
