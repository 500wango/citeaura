Crawl access — infrastructure note

GPTBot Blocked by robots.txt? Find and Fix the Rule

GPTBot follows robots.txt, so one broad Disallow can keep product pages out of a crawler's view. This note walks through the parts that usually cause confusion — longest-match paths, User-agent precedence, and Allow-vs-Disallow ties — then gives you copy-paste curl -A checks, cache and canonical-host checks, and a way to read the logs. CiteAura's site audit can turn a detected block into a ticket with an acceptance check; your infrastructure team still makes the change.

How robots.txt is actually evaluated

Every robots.txt check is per-host, per-path, and per-User-agent-group. A crawler fetches https://yourdomain.com/robots.txt (always at the origin root, not in a subdirectory), parses it into groups, selects the single most-specific matching group for its own token, then evaluates that group's rules in longest-match order against the requested path. There is no site-wide inheritance, no glob recursion beyond the $ and * wildcards defined in RFC 9309, and no cross-host merging.

OpenAI documents three distinct crawlers with separate tokens:

  • GPTBot — training-data crawl. UA string contains GPTBot.
  • OAI-SearchBot — search-index retrieval for ChatGPT Search.
  • ChatGPT-User — live browsing triggered by a user prompt inside ChatGPT.

If you only unblock GPTBot but leave a Disallow: / on OAI-SearchBot, ChatGPT Search will still miss your pages even though training crawl succeeds. Always decide the policy per-token.

The longest-match rule

The original 1994 robots.txt spec said "first match wins." RFC 9309 (September 2022, now the IETF standard) and the de-facto Google/OpenAI implementation use longest-match wins. Within the selected User-agent group, the rule with the longest matching path decides, and if two rules have the same path length, Allow beats Disallow.

This matters because a naive file like this does not protect /app/ the way the author thought:

User-agent: GPTBot
Allow: /
Disallow: /app

Request for /app/dashboard: both rules match (/ length 1, /app length 4). Longest wins → Disallow: /app (length 4) → blocked. Correct. But consider:

User-agent: GPTBot
Allow: /docs/
Disallow: /

Request for /docs/api: Allow: /docs/ (length 6) beats Disallow: / (length 1) → allowed. Request for /pricing: only Disallow: / matches → blocked. If you added Allow: / hoping to "open the site," it would not override the longer /app/ disallow — longest still wins. You need to reason per-URL, longest path first.

Wildcards change length calculation. * matches any sequence, $ anchors to end-of-URL:

User-agent: GPTBot
Disallow: /*?utm_*
Allow: /products/$

Here /products/ would match the Allow: /products/$ only for the exact path /products/, not /products/widget. Use $ sparingly and test each URL explicitly.

Rule of thumb: List the five public URLs you care about (/, /pricing, /products/*, /docs/*, /blog/*). For each, find the longest Allow and longest Disallow that prefix-match the path. The longer of the two decides. If equal length, Allow wins.

User-agent precedence: why GPTBot sees a different file than you do

Robots.txt groups are selected by most-specific match, not first-match and not merged. The algorithm:

  1. Split the file into groups. A group is one or more User-agent: lines followed by rule lines until the next User-agent: or end of file.
  2. For the crawler's token (e.g., GPTBot), collect every group where one of its User-agent values is a case-insensitive substring match. GPTBot matches GPTBot exactly; * matches everything but with lowest specificity.
  3. If more than one group matches, the group with the longest (most specific) User-agent string wins. All other groups are ignored entirely — they are not merged.
  4. If no group matches, the crawler is allowed everywhere (empty allow).

Example that traps teams:

# Group 1 — blanket block inherited from staging
User-agent: *
Disallow: /

# Group 2 — attempted fix
User-agent: GPTBot
Allow: /

For GPTBot: Group 2 (GPTBot, length 6) beats Group 1 (*, length 1) → only Group 2 rules apply → allowed. This works as intended.

But this does not:

User-agent: *
Allow: /

User-agent: GPTBot
Disallow: /private/
Disallow: /app/

For GPTBot, only the GPTBot group applies. That group does not inherit Allow: / from the * group. Since the GPTBot group has no explicit Allow: /, the default is "implicit allow" for any path not matched by a Disallow — so /pricing is allowed, but only because it falls through, not because the * group said so. If you later reorder or combine groups with blank lines, parsers may merge them unpredictably. Keep each group's intent self-contained and put the most-specific group first for human readability.

Case insensitivity: gptbot, GptBot, and GPTBot are equivalent. Spelling matters though — GPT-Bot or ChatGPTBot will not match OpenAI's crawl.

For completeness, a group with multiple User-agent lines applies to any of them with equal specificity:

User-agent: GPTBot
User-agent: OAI-SearchBot
Allow: /
Disallow: /app/

This single group serves both tokens. Preferred for a uniform public-page policy; split into separate groups only if you need different paths per token.

Allow vs Disallow: debugging when your fix does nothing

Adding an Allow does not cancel a broader Disallow unless the Allow path is longer (more specific) for the URL you tested. The three failure modes we see most often:

1. Allow is shorter than Disallow — still blocked

User-agent: GPTBot
Disallow: /products/
Allow: /

/products/widget matches both; Disallow length 10 > Allow length 1 → blocked. Fix: allow the specific subtree, not the root.

User-agent: GPTBot
Disallow: /internal/
Allow: /products/
Allow: /pricing
Allow: /docs/

2. Allow and Disallow have identical length — Allow wins, but only for that exact prefix

User-agent: GPTBot
Disallow: /api/
Allow: /api/

Equal length (5) → Allow wins for /api/ paths → allowed. This is per RFC 9309, but some older testers flag it as a conflict. Prefer removing the contradictory Disallow rather than relying on tie-break.

3. A longer Disallow hidden in the same group

User-agent: GPTBot
Allow: /blog/
Disallow: /blog/drafts/
Disallow: /

/blog/hello-world → Allow /blog/ length 6 vs Disallow / length 1 → allowed. /blog/drafts/secret → Disallow /blog/drafts/ length 13 vs Allow length 6 → blocked. This is correct and intentional — the lesson is to enumerate subordinate paths.

Debug procedure: For each blocked URL you care about, run this mental longest-match filter:

  1. Pick the winning User-agent group.
  2. Collect every Allow and Disallow whose path is a prefix of the URL (with wildcard expansion).
  3. Find the longest matching Allow length (L_a) and longest matching Disallow length (L_d).
  4. If neither matches → allowed. If only one side matches → that side decides. If both match → longer length wins; if tied, Allow wins.

When in doubt, use Google's open-source robotstxt parser locally — OpenAI and Google share longest-match semantics, so it is a reliable offline oracle:

# Quick offline check with Google's parser (Python)
pip install robotstxt-parser  # or use the Go port
python -c "
from urllib.robotparser import RobotFileParser
rp = RobotFileParser()
rp.parse(open('robots.txt').read().splitlines())
for path in ['/', '/pricing', '/app/dashboard', '/products/widget']:
    print(path, rp.can_fetch('GPTBot', path))
"

Removing a stale Disallow: / is almost always cleaner than stacking three Allow lines to punch holes in it. Prefer an explicit allow-list over block-list hole-punching.

How to tell GPTBot is blocked — with curl -A verification

Do not trust the browser address bar. Browsers send no crawler User-agent, so they hit the * fallback (if any) rather than the GPTBot group. You need to fetch the file as GPTBot.

The exact tokens to test

OpenAI publishes these UA substrings (case-insensitive). Test all three if you care about ChatGPT visibility end-to-end:

GPTBot
OAI-SearchBot
ChatGPT-User

Full UA strings seen in the wild look like:

Mozilla/5.0 AppleWebKit/537.36 (KHTML, like Gecko); compatible; GPTBot/1.2; +https://openai.com/gptbot
Mozilla/5.0 AppleWebKit/537.36 (KHTML, like Gecko); compatible; OAI-SearchBot/1.0; +https://openai.com/searchbot
Mozilla/5.0 AppleWebKit/537.36 (KHTML, like Gecko); compatible; ChatGPT-User/1.0; +https://openai.com/bot

For robots.txt matching, the substring (GPTBot) is enough because the match is substring-based. Use the short token with curl -A for clarity.

Step-by-step curl verification

# 1. Fetch as seen by GPTBot on the canonical host — bypass local cache
curl -sSL -A "GPTBot" -H "Cache-Control: no-cache" https://yourdomain.com/robots.txt -D - -o /tmp/robots.gptbot.txt
cat /tmp/robots.gptbot.txt

# 2. Same file as OAI-SearchBot (ChatGPT Search path)
curl -sSL -A "OAI-SearchBot" -H "Cache-Control: no-cache" https://yourdomain.com/robots.txt -o /tmp/robots.searchbot.txt
diff -u /tmp/robots.gptbot.txt /tmp/robots.searchbot.txt || echo "Groups differ per crawler"

# 3. Compare against a generic browser fetch — are you even serving the same file?
curl -sSL -H "Cache-Control: no-cache" https://yourdomain.com/robots.txt -o /tmp/robots.browser.txt
diff -u /tmp/robots.browser.txt /tmp/robots.gptbot.txt && echo "No UA-based branching (good)"

# 4. Check HTTP semantics — robots.txt must be 200, not 301/302 to another host
curl -sSI -A "GPTBot" https://yourdomain.com/robots.txt | head -n 20
# Expect: HTTP/2 200, Content-Type: text/plain, no x-robots misrouting

# 5. Test a protected path header — does the server also send X-Robots-Tag?
curl -sSI -A "GPTBot" https://yourdomain.com/pricing | grep -i "x-robots-tag\|robots"
# If you see "noindex" here, robots.txt allow alone won't make the page indexable

Interpreting the first fetch: look for the group that names GPTBot or OAI-SearchBot. If only User-agent: * exists, that group governs GPTBot too (lowest specificity). If a Disallow: / appears in the winning group, every product URL is blocked regardless of what other groups say.

A WAF challenge (Cloudflare "Checking your browser," DataDome, Akamai Bot Manager) can look identical to a robots block from the model's perspective — the crawler gets a 403 or a JS challenge instead of HTML. Fix robots.txt first because it is deterministic and cheap; then verify the HTML fetch succeeds with a real HTTP 200 and non-empty body.

Canonical-host check: the silent redirect trap

Robots.txt is per-host and per-scheme. https://example.com/robots.txt and https://www.example.com/robots.txt are different files served by different vhosts. The canonical host — the one your <link rel="canonical">, sitemap, and og:url point to — is the only file that matters. A perfect fix on the apex that never gets served because all traffic 301s to www is a phantom fix.

# Which host is canonical? Follow redirects and compare
curl -sSI https://example.com/robots.txt | grep -E "HTTP|Location"
curl -sSI https://www.example.com/robots.txt | grep -E "HTTP|Location"
# If one returns 301 → https://www.example.com/robots.txt, that target is the canonical file

# Verify both hosts, both schemes if you still serve http
for host in example.com www.example.com; do
  echo "=== $host ==="
  curl -sSL -A "GPTBot" -H "Cache-Control: no-cache" "https://$host/robots.txt" | head -n 30
done

# Cross-check against the canonical link on a public page
curl -sSL https://www.example.com/pricing | grep -i 'rel="canonical"'
# The host in that href must match the robots.txt you just fixed

Also verify you do not have a stray robots.txt at a path like /app/robots.txt shadowing expectations — crawlers never look there. And confirm https vs http: if you 301 http:// to https:// at the edge, the edge's 301 response for the old scheme's robots.txt is irrelevant as long as the https file is correct.

Deploy target: Fix the file on the host that the redirect chain terminates at. Then re-fetch with curl -L to confirm the final 200 body is your edited file, not a cached 301 page.

How to fix the file correctly

  1. Keep private routes closed. /app/, /admin/, /account/, /cart/, /api/, /internal/ stay disallowed. Do not open them to punch a hole for marketing pages.
  2. Allow the public product subgraph. Homepage, product, pricing, docs, blog, comparisons, and any page that states official facts.
  3. Add an explicit GPTBot family group if the blanket * rule is too coarse to edit safely. This isolates the AI crawler policy without touching the Googlebot/Microsoftbot policy that SEO owns.
  4. Deploy to the canonical host, including the www/apex target your redirects land on.
  5. Fetch the live file again with curl -A. Do not trust a staging copy or an edge cache you have not purged.

A minimal, production-safe pattern for a SaaS marketing site:

# Public product pages — open to OpenAI crawlers
User-agent: GPTBot
User-agent: OAI-SearchBot
User-agent: ChatGPT-User
Allow: /
Disallow: /app/
Disallow: /admin/
Disallow: /account/
Disallow: /cart/
Disallow: /api/
Disallow: /internal/

# Everyone else — keep existing policy (example)
User-agent: *
Allow: /
Disallow: /app/
Disallow: /admin/
Sitemap: https://www.example.com/sitemap.xml

If you already maintain a permissive * group, the OpenAI-specific group is optional — GPTBot would inherit the * allow. Add it anyway when (a) you want to document the AI-crawler decision explicitly, (b) legal wants a separate audit trail, or (c) you anticipate tightening * later for other bots without re-blocking OpenAI.

An alternative "allow only what you need" pattern for locked-down sites:

User-agent: GPTBot
Allow: /$
Allow: /pricing$
Allow: /products/
Allow: /docs/
Allow: /blog/
Allow: /comparisons/
Disallow: /

Here Disallow: / is intentionally broad but the longer Allow paths win for the listed public URLs via longest-match. This is valid but harder to maintain — every new public section needs a new Allow line. Prefer the first pattern unless your security posture requires default-deny.

Caddy and Cloudflare cache pitfalls

Most "I deployed the fix but GPTBot is still blocked" reports are cache illusions. Robots.txt is a small text file that every cache layer loves to hold.

Cloudflare

  • Edge cache: Cloudflare caches /robots.txt under your Cache Rules or the default .txt heuristic. After deploy, purge that URL only: Dashboard → Caching → Purge Cache → Custom Purge → https://www.example.com/robots.txt. A full-site purge works but is unnecessary.
  • Cache-TTL on the origin header: If origin sends Cache-Control: max-age=86400, Cloudflare will respect it even after you purged once — the next fetch re-caches the stale origin file if your deploy pipeline is behind. Set Cache-Control: max-age=3600, must-revalidate for /robots.txt specifically, or add a Cloudflare Cache Rule: Path /robots.txt → Cache eligibility: Bypass or TTL 1 hour.
  • Transform / Worker rewriting: A Worker that injects security headers or rewrites User-agent: * responses can accidentally serve a synthetic robots.txt to bots but the real file to browsers. Test with curl -A GPTBot through Cloudflare (cf-cache-status: HIT/MISS/BYPASS in response headers) and directly against origin (bypass via hosts override or cf-connecting-ip test) to spot divergence.
# Is Cloudflare still serving the old file?
curl -sSI -A "GPTBot" https://www.example.com/robots.txt | grep -i "cf-cache-status\|age\|cache-control"
# HIT + old Age → purge needed. BYPASS/MISS + new body → you are live

# Force a cache-bypass fetch via Cloudflare (but not a purge)
curl -sSL -A "GPTBot" -H "Cache-Control: no-cache" -H "Pragma: no-cache" \
  https://www.example.com/robots.txt | head -n 40

Caddy

  • file_server root mismatch: Caddy's file_server serves robots.txt from the site root you configured. If Caddyfile points root * /srv/www but your deploy writes to /srv/app/public, the file never updates. Verify root and handle_path /robots.txt if you use it.
  • handle / reverse_proxy shadowing: A reverse_proxy for / can intercept /robots.txt before file_server sees it. Order matters in Caddy — put an explicit handle /robots.txt { file_server } before the catch-all proxy, or serve robots via respond.
  • No edge cache, but local file cache: Caddy itself does not cache static files aggressively, but if you run caddy file-server --root behind another nginx/Varnish, that layer may.
# Caddyfile — ensure robots.txt is served from disk, not proxied
www.example.com {
  root * /srv/www
  handle /robots.txt {
    file_server
    header Cache-Control "public, max-age=3600, must-revalidate"
    header Content-Type "text/plain; charset=utf-8"
  }
  handle {
    reverse_proxy localhost:3000
  }
}

# After deploy, reload without dropping connections
caddy reload --config /etc/caddy/Caddyfile --adapter caddyfile

# Verify on the origin host itself (bypass Cloudflare)
curl -sSL -A "GPTBot" http://127.0.0.1:2019/robots.txt 2>&1 | head
# or if origin listens on 80/443 locally:
curl -sSL -A "GPTBot" --resolve www.example.com:443:127.0.0.1 https://www.example.com/robots.txt | head -n 40

General rule: after any fix, expect up to 24 hours of crawler-side caching even after your edge is purged. OpenAI, like Google, caches robots.txt per host for up to 24h. A re-fetch with curl proves your server is correct; it does not force the crawler to re-evaluate instantly. Schedule a re-crawl or wait one cache window before declaring failure.

Log analysis: proving GPTBot actually arrived

Fixing the file is half the job. You need evidence the crawler came back and got a 200.

What GPTBot looks like in logs

Look for these signals in your access log (Caddy JSON logs, nginx combined, Cloudflare Enterprise Log Share, or WAF logs):

# Caddy JSON log — filter for GPTBot
journalctl -u caddy --since "7 days ago" | grep -i "gptbot"

# nginx / Caddy combined — case-insensitive UA match
grep -i "gptbot" /var/log/nginx/access.log | tail -n 20
grep -i "oai-searchbot\|chatgpt-user" /var/log/nginx/access.log | tail -n 20

# Cloudflare — if you ship logs to R2/S3/BigQuery, search userAgent field
# userAgent contains "GPTBot" and ray / cfBotManagement.verifiedBot == true for verified bots

# General — count hits per token over last 14 days
grep -i "gptbot" /var/log/caddy/access.log | wc -l
grep -i "oai-searchbot" /var/log/caddy/access.log | wc -l

A typical GPTBot hit:

23.102.140.112 - - [18/Aug/2026:14:22:05 +0000] "GET /pricing HTTP/1.1" 200 18432 "-" "Mozilla/5.0 AppleWebKit/537.36 (KHTML, like Gecko); compatible; GPTBot/1.2; +https://openai.com/gptbot"

Verify the IP via reverse DNS if you need to rule out spoofing (anyone can set User-agent: GPTBot):

# Reverse + forward confirm for a suspected GPTBot IP
host 23.102.140.112
# Expect *.openai.com or *.search.msn.com (for some Bing-sourced crawls) — OpenAI publishes ranges
dig +short -x 23.102.140.112
host gptbot.openai.com  # forward check of claimed hostname if rDNS returns one

Cloudflare's cfBotManagement.verifiedBot and the cf-wrapper: verified_bot header are more reliable than rDNS alone when you are behind Cloudflare.

Interpreting absence

  • No GPTBot hits at all in 7–14 days post-fix — the crawler has not re-attempted. Normal if your site is low-frequency. Trigger a re-crawl via a fresh sitemap ping or a ChatGPT browsing prompt that requests the URL.
  • Hits for /robots.txt but not for /pricing — robots.txt fetch succeeded (200) but the path is still disallowed per longest-match. Re-audit the group logic.
  • Hits with 403/429/503 — WAF, rate-limit, or origin error, not a robots.txt allow. Fix that layer next.
  • Hits with 200 but empty or shell HTML — crawler got the page but it is a JS shell. Robots allow is not enough; the HTML must contain the product facts. See Why ChatGPT Does Not Mention Your Brand.

Keep the evidence window aligned: compare log hits after the verified deploy timestamp and after the edge purge. A hit from before the fix tells you nothing about after.

Verification and logs

Run this end-to-end after every robots.txt deploy. Replace www.example.com with your canonical host.

HOST="www.example.com"
curl -sSI -A "GPTBot" -H "Cache-Control: no-cache" "https://${HOST}/robots.txt"
curl -sSL -A "GPTBot" "https://${HOST}/robots.txt" | tee /tmp/robots.live.txt
for path in / /pricing /products/ /docs/ /blog/; do
  curl -sSL -A "GPTBot" -o /dev/null -w "$path %{http_code}\n" "https://${HOST}${path}"
done

Use the output as the acceptance evidence: the canonical host serves the edited file, public paths return 200, and private routes remain protected. Keep a fuller CI or proxy-specific script in your infrastructure documentation.

Other crawler policies

OAI-SearchBot, ChatGPT-User, ClaudeBot, PerplexityBot and CCBot have separate policies. Decide them deliberately; an allow rule for GPTBot does not change any other crawler's access.

If the homepage is a JavaScript shell, opening robots is not enough. See Why ChatGPT Does Not Mention Your Brand for extractability checks after the crawler is allowed in.

A crawl allow is not a ranking promise

Opening robots.txt lets a compliant crawler request the page. It does not guarantee that ChatGPT will fetch it, retrieve it at query time, mention it, cite it, or rank it. Retrieval depends on index freshness, query relevance, and the model's retrieval policy; citation depends on product surface and whether browsing was invoked; ranking depends on comparison with every other eligible source.

Treat the fix as a prerequisite and measure the effect with a labeled cohort. Fix robots, purge cache, confirm 200s, wait one crawler cache window, then run the same question set again and compare mention rates within that cohort. A higher mention rate on a fixed question set is evidence about that sample — not a promise for every user prompt.

FAQ: GPTBot and robots.txt

Should GPTBot be allowed to crawl every route?

No. Keep app, admin, account, cart, API, and other private routes closed. Allow only public pages that state the product. A crawler that can reach /app/ or /api/ is a security and cost issue, not a visibility win.

How do I confirm a GPTBot robots.txt fix with curl?

Fetch the live robots.txt on the canonical host with curl -A GPTBot -H "Cache-Control: no-cache" https://www.example.com/robots.txt, verify the longest-match Allow wins for each public path, check the canonical-host redirect chain, purge Cloudflare's cache for that URL, and confirm Caddy serves the file from the correct root with caddy reload.

Will an allowed crawler guarantee a ChatGPT mention?

No. An allow rule removes a crawl block; it does not guarantee retrieval, a citation, a mention, or a ranking. Availability after the fix must be measured with a labeled question cohort.

Why does my fix not appear even after deploy?

Usually Cloudflare edge cache or a Caddy reverse_proxy shadowing the file. Purge /robots.txt in Cloudflare, ensure Caddy's handle /robots.txt { file_server } precedes the proxy catch-all, set Cache-Control: max-age=3600, must-revalidate, and re-fetch with curl -H "Cache-Control: no-cache" through the edge and directly against origin to compare.
