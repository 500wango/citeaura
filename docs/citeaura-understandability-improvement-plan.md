# CiteAura 易懂性改进计划

日期：2026-09-06

## 目标

让第一次使用的老板或营销人员，不需要现场讲解，就能回答四个问题：

1. 发生了什么？
2. 为什么值得关注？
3. 现在先做什么？
4. 怎样知道有进展？

技术证据、采样模式和原始回答继续保留，但按需展开，不让用户先理解 GEO 术语才能行动。

## 非目标

- 不新增采样平台、自动发布集成或移动端。
- 不把示例数据包装成真实结果。
- 不删除原始回答、引用、时间戳和采样模式等溯源信息。
- 不为老板、营销、技术人员建立三套互相分叉的产品流程。
- 不在没有真实客户证据前扩展复杂预测、归因或 ROI 承诺。

## 产品原则

### 1. 先结论，后证据

每个主要页面先显示一条自然语言结论，再提供数字、样本和原始回答作为展开内容。

### 2. 每个结论必须连接一个动作

发现、原因、建议、负责人、验收方式和当前状态必须能沿同一条记录查看，不能让用户在多个模块之间自行拼接。

### 3. 明确事实、推断和未测量

界面统一区分：已观察到的事实、基于证据的解释、尚未验证的假设、未测量状态。禁止用单一总分掩盖证据不足。

### 4. 同一数据，分层阅读

老板看到影响和进展，营销人员看到页面和内容动作，技术人员展开原始证据；三者消费同一 finding/ticket/evidence 记录。

## 分阶段计划

### P0：重做首次价值路径

**目标：** 用户在工作台首屏理解当前状态和下一步。

**改动：**

- 将 Overview 顶部改为“当前结论”区域：一句话结论、证据范围、可信程度、下一动作。
- 将 `AI Mention Rate`、`Technical Audit Grade` 等指标改成带解释的业务标签；保留原始指标作为详情。
- 将首要行动限制为一个推荐动作，说明原因、预计涉及页面/问题和完成条件。
- 对无样本、单周期、单平台和合成基准统一显示限制说明。
- 将 `Setup checklist`、`Visibility baseline`、`Implementation backlog` 合并成一条状态链，避免多个“下一步”。

**验收：** 新用户仅看首屏，能复述“目前发现、证据是否充分、下一步是什么”。

### P0：建立 Finding → Ticket → Verification 详情

**目标：** 用户不需要口头解释就能执行最高优先级问题。

**改动：**

- 每条 finding 显示：问题、影响范围、证据、解释置信度、建议动作、负责人、验收方式。
- 工单详情显示关联的 URL、问题/Prompt、原始回答或审计证据，以及“完成后检查什么”。
- 明确区分“已完成修改”“已通过网站验收”“AI 结果已复测”三个状态。
- 从 Overview、Plan、Report 进入同一条详情，不复制三套文案。

**验收：** 营销人员能从一条 finding 直接知道改哪个页面、改什么、交给谁；老板能看到是否已经证明有效。

### P1：为老板和营销人员提供阅读层级

**目标：** 同一页面既可快速决策，也能继续深入。

**改动：**

- 默认折叠原始回答、引用列表和技术字段。
- 增加“为什么这样判断”展开区，显示事实、推断和缺失证据。
- 将术语改为“业务解释 + 原术语”，例如“AI 推荐率（Mention Rate）”。
- 把成功、失败、未测量、待审核和演示数据使用固定状态标签及颜色。

**验收：** 不懂 GEO 的用户不看术语说明也能完成主要操作；技术用户展开后仍能追溯到样本。

### P1：把进展改成可验证的变化

**目标：** 用户能判断工作是否产生进展，而不是只看到工单数量。

**改动：**

- 以同一问题、平台、模型、采样模式和时间窗口展示 before/after。
- 分开展示：网站整改进度、验收通过率、AI 结果变化、尚未可归因的变化。
- 没有可比周期时显示“尚无趋势结论”，不绘制误导性上升/下降图。
- 在结果旁显示样本数、来源和采样时间。

**验收：** 用户能明确说出“完成了什么”“测到了什么”“还不能证明什么”。

### P1：交付包改成客户可读的叙事

**目标：** 客户打开交付包即可理解，不需要产品人员翻译。

**改动：**

- 报告开头固定为：现状、最重要发现、建议先做的三件事、证据限制。
- 每条工单包含业务解释和技术验收，不只输出内部 action code。
- 将“诊断就绪”“可见度已测量”“实施资产可发布”继续分开显示。
- 保留原始证据作为附录，不让附录承担主叙事。

**验收：** 外部读者能从报告中独立复述结论和下一步，且不会把诊断就绪误读为已完成发布。

## 实施顺序

1. 先用一个真实项目走完整流程，记录所有需要人工解释的断点。
2. 完成 Overview 的结论和单一下一动作。
3. 完成 Finding/Ticket/Verification 贯通详情。
4. 补齐术语、证据层级和状态标签。
5. 最后调整报告叙事和 before/after 展示。

每一步只改现有页面和数据契约能够支持的范围；若发现数据不足，先显示未测量或待审核，不用文案掩盖缺口。

## 衡量标准

首批 5 个真实用户验证以下指标：

- 首次进入工作台后，能否在 2 分钟内说出当前发现和下一动作；
- 是否能独立打开最高优先级工单并找到对应页面/证据；
- 是否能区分“修改完成”和“效果已证明”；
- 从诊断到首次执行动作所需时间；
- 第二次打开产品时是否直接回到未完成动作，而不是重新理解界面。

若用户仍需要人工解释同一概念两次以上，优先修正文案、信息层级或记录关联，不新增功能。

## 暂停条件

完成 P0 后若真实用户仍不愿执行工单，或无法说出产品带来的具体决策价值，应暂停扩展功能和推广投入，重新访谈目标客户与调整切入场景。
