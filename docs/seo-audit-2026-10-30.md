## 1. 执行摘要

### 1.1 当前最重要的三件事

1. **优先改进已有曝光页面，而不是扩量或重复提交索引。** GSC 最近一次短窗口导出为 1,210 次曝光、3 次点击、平均排名 39.7；部分法语查询已到平均第 7 位附近，但仍无可见查询点击。需要按查询、页面、国家、设备拆分，分别检验排名不足与搜索结果吸引力，不应一律归因为标题问题。
2. **补足内容的可核验证据与上下文内链。** 比较内容应给出具名产品、来源日期、适用场景与局限；不能用匿名竞品类别的负面断言代替测试。用现有问题诊断文、免费工具、样本报告衔接产品页面，优先完善已有资产，不按字数指标批量扩写。
3. **先做可复现的技术验证，再实施性能改动。** 现有 68 个 sitemap URL 可抓取，5 个关键 URL 已被 Google 索引。性能测试存在超时警告，尚不能将 Speed Index 异常归因于 `.reveal`、跑马灯或源站。页脚对比度和图片尺寸适配有明确的改进线索；HTML 边缘缓存需单独做安全配置与对照试验。

### 1.2 不应继续使用的结论

- “Common Crawl 没抓到，所以任何 AI 都不可能引用 CiteAura”——**不成立**。
- “Wayback 首次记录在 10 月 13 日，所以网站只有 17 天”——**不成立**；9 月 GSC 已有搜索曝光。
- “5 个 URL 已索引，因此全站索引健康度满分”——**超出抽样范围**。

- “Speed Index 一定由 reveal / 跑马灯造成；修好必达 3 秒以内”——**未验证**。

## 4. 技术、可访问性与性能事实

### 4.1 本次通过的基础检查

- 68 个 sitemap URL 最终均返回 HTTP 200，无已证实的持续 4xx / 5xx。
- 68 页 title、description 无缺失及完全重复，描述长度为 102–160 字符；canonical 均与清单 URL 一致。
- 有 18 个 title 超过 60 字符，最长 73；这只是长度观察，不是违规或排名失败阈值。
- 首页英文和法文版各有一个 H1。元数据脚本中的 `n_h1` 实际统计 H1 文本分段，不能把 `<br>` 分出的两个文本节点当作两个 H1。
- `http://citeaura.com/` → HTTPS 为 308；`https://www.citeaura.com/` → 主域为 301；HTTP www 变体经过两跳规范化。
- 未知路径返回 404；抽样营销页原始 HTML 含正文及 pricing / docs 链接，不是只有空 SPA 壳。
- `/app` 被排除在 sitemap 外；观测到 `X-Robots-Tag: noindex, nofollow` 和 robots 禁止抓取。私有 API 样例返回 401。
- 首页响应含 CSP、HSTS、`nosniff`、Referrer-Policy、Permissions-Policy。这里只确认头部存在，不替代完整安全审查。

robots 禁止抓取与 noindex 是不同控制：被禁止抓取时，爬虫可能无法读取 noindex。不能称这两项叠加为“绝对不会索引”；敏感数据必须依靠认证授权而非 robots。

### 4.2 缓存与网络测量

- 多次首页及营销页请求返回 `cf-cache-status: DYNAMIC`。
- 响应含 `Cache-Control: public, max-age=0, s-maxage=3600, stale-while-revalidate=86400`；当时抽样响应未见 `Set-Cookie`。
- 从测试机器发出的 curl 请求，常见 TTFB 约 0.85–1.16 秒，部分首轮请求约 2.45–2.69 秒；存在偶发连接重置，重试后成功。
- 这些数字包含网络往返等成本，**不能写成“源站 SSR 耗时约 1 秒”**。大多数英文页实际由 FileResponse 服务，法文首页有 SSR 缓存。
- `DYNAMIC` 说明这些请求未命中边缘 HTML 缓存，但不能单凭它确定 Cloudflare 规则的完整配置，也不能证明它造成某次 Speed Index 异常。
- 若实施缓存，采用公开营销路径白名单，排除认证态、API、app、admin、files、运行时及用户相关响应，验证查询参数、语言、Cookie、Authorization 与清缓存策略。**不沿用此前过宽的负向正则作为生产规则。**

## 10. 复测与监控方案

### 10.1 部署前

1. 保存当前 git diff 和选定页面基线；不要覆盖用户或其他会话改动。
2. 核对 sitemap 与真实公开路由、canonical；不能把本机静态一致性当线上验证。

### 10.2 部署后技术验收

- 用 HTML 解析器而非贪婪正则抽取 title、meta、canonical、hreflang、H1。
- 检查修改路径 HTTP 200、旧法语路径跳转、新 canonical 与语言关系；检查未知路径仍为 404。
- 若修改缓存，验证匿名公开页 HIT / Age，及登录、授权、API、app、admin、files 响应不被共享缓存；确认内容更新可失效。
- 至少 3 次同环境移动端性能运行，记录 Lighthouse / Chrome 版本、区域、网络节流、时间、警告和中位数；存在超时时先处理超时，不据总分做成功承诺。
- 对照度、图片传输和交互分别验收；需要真实 CWV 时另取 field 数据。

### 10.3 搜索与业务观察

- 部署后 7–14 天：观察已改 URL 是否重新抓取、canonical 是否一致；这是检查窗口，不是 Google 处理时限保证。
- 部署后 4–8 周：按同长度窗口和相同查询 / 页面 / 国家 / 设备维度观察曝光、排名、CTR；保留对照页和页面变更记录。

- AI 引用采样固定 prompt 集合、平台 / 模型版本、地区、时间和采样模式，分别记录“API·参数化知识”“API·联网检索”“人工·产品端”。单次回答不是稳定排名或全站引用率。

### 10.4 回滚边界

仓库改动与 Cloudflare / 第三方配置分别保留回滚记录。若出现错误缓存私有数据、公开页 noindex / canonical 回归、持续 4xx / 5xx，优先停止该项变更并恢复已验证版本；不得为追求审计分数覆盖其他人的工作。
